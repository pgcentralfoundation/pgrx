# v20.0 Migration Guide

This release fixes pgrx APIs that let safe code cause undefined behavior, and
APIs that failed on valid input. The sections below describe the fixes that
change a signature or behavior. For the move from pgrx's handwritten C macro
ports to the generated macros, see
[Using PostgreSQL C Macros](docs/src/extension/c-macros.md#migrate-handwritten-helper-calls).

## Heap tuple helpers

`pgrx::htup::composite_row_type_make_tuple` is now an `unsafe fn`: the caller
must pass a live composite Datum. It also fully detoasts the row, so a stored
composite with a one-byte header is read correctly.

## `PgVarlena`

`PgVarlena<T>` now holds its value in Rust. Reading one from a Datum copies the
payload into storage aligned for `T`, because PostgreSQL does not align a
varlena's payload, and keeps no pointer into PostgreSQL memory. The value may
therefore outlive the Datum, memory context, or SPI connection it was read
from. `into_pg` and `IntoDatum` allocate a new varlena in `CurrentMemoryContext`
each time, even for an unchanged value, rather than returning the Datum the
value was read from. Payload bytes after the `T` are copied back unchanged.

`PgVarlena::new` now requires `T: Default` and starts from `T::default()`. It
used to start from zero bytes, which is undefined behavior for a `T` that has no
all-zero value, such as a reference or an enum without a zero discriminant.
Build the value and convert it with `PgVarlena::from(value)`, derive or
implement `Default`, or call the `unsafe` `PgVarlena::new_zeroed` where all-zero
bytes are a valid `T`.

## SPI status codes

`SpiOkCodes` has a `MergeReturning` variant on PG17 and later, so SPI accepts
`MERGE ... RETURNING` instead of panicking on its status code.
