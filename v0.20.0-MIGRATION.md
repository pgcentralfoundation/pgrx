# v0.20.0 Migration Guide

This release fixes pgrx APIs that let safe code cause undefined behavior, and
APIs that failed on valid input. The sections below describe the changes to
supported versions, build requirements, signatures, and behavior that can need
updates in an extension.

## Upgrading

pgrx now needs Rust 1.99.1 or newer. Update Rust, install the new `cargo-pgrx`,
then update your crate's dependencies:

```bash
rustup update stable
```

```bash
cargo install cargo-pgrx --version 0.20.0 --locked
```

```bash
cargo pgrx upgrade
```

The new `cargo-pgrx` also fixes `cargo pgrx upgrade` without `--to`, which
failed on Cargo 1.85 and newer. Builds also need a `clang` driver from the same
LLVM release as `libclang`, and should have that release's `llvm-ar`; see
[Build requirements](#build-requirements). An existing `cargo pgrx init`
configuration keeps working. Its entries for PostgreSQL 13 and 14 are ignored,
and those installations stay on disk. To replace a PostgreSQL 19 beta that
`cargo pgrx init` downloaded with 19rc1, run `cargo pgrx init --pg19=download`.

## PostgreSQL 13 and 14

Remove the `pg13` and `pg14` features from your extension's `Cargo.toml`,
code gated on `feature = "pg13"` or `feature = "pg14"`, and CI jobs for those
versions. If `default` names one of them, change it to a supported version.

```toml
# Before
[features]
default = ["pg13"]
pg13 = ["pgrx/pg13", "pgrx-tests/pg13"]
pg14 = ["pgrx/pg14", "pgrx-tests/pg14"]
pg15 = ["pgrx/pg15", "pgrx-tests/pg15"]

# After
[features]
default = ["pg15"]
pg15 = ["pgrx/pg15", "pgrx-tests/pg15"]
```

## Build requirements

pgrx requires Rust 1.99.1 or newer, up from 1.96, and Cargo refuses to build it
with an older toolchain. Rust 1.99.0 is excluded because it can miscompile an
`extern "C"` function that returns `bool` on x86_64
([rust-lang/rust#163911](https://github.com/rust-lang/rust/issues/163911)), and
pgrx passes such functions to PostgreSQL. Update any `rust-toolchain.toml` or
CI job that pins an older release.

`pgrx-pg-sys` now generates the C macros during every build, and a failure to
generate them stops the build with an error that names the cause. It needs:

- A `clang` driver whose major version matches `libclang`, and the `llvm-ar`
  from the same LLVM release, or `llvm-lib` for Windows targets. On
  Debian-likes, install `clang llvm libclang-dev`. On RHEL-likes, install
  `clang llvm`. Without an LLVM archiver, Unix builds fall back to the system
  `ar`, which works for native builds but may not index objects built for
  another target.
- On Linux and macOS, a host C compiler, which builds the generator's SHA-256
  backend. Before, one was needed only with the `cshim` feature.

The `clang` driver also compiles pgrx's native support archive, which now
includes wrappers for PostgreSQL's static inline functions in every build,
with or without `cshim`.

pgrx uses `CLANG_PATH` when it is set. Otherwise it uses the first match among
the `CLANG` that a `pg_config` program's `--configure` output records, the
`clang` installed with `libclang`, and `clang-<major>` or `clang` on `PATH`.
A driver that loads a default configuration file, as Gentoo's Clang does, is
refused. Set `CLANG_NO_DEFAULT_CONFIG=1` to build without that file. See
[System Requirements](README.md#system-requirements).

## Cross-compiling

A cross build needs PostgreSQL server headers configured for the target, and
pgrx now refuses headers configured for another machine. Select the target's
headers with `PGRX_INCLUDEDIR_SERVER_PG<NN>_<target>`, describe the target
with `PGRX_PG_CONFIG_AS_ENV`, or import a complete target bundle with
`PGRX_TARGET_INFO_PATH_PG<NN>`. Use `BINDGEN_EXTRA_CLANG_ARGS_<target>` to
pass the target's sysroot to `clang` when it cannot find it. The
[cross-compiling guide](docs/src/extension/build/cross-compile.md) describes
each path and what pgrx checks.

## Handwritten C macro helpers

pgrx's Rust ports of PostgreSQL macros and static inline functions, such as
`pgrx::varsize_any`, `check_for_interrupts!`, `pg_sys::heap_tuple_get_struct`,
and the `pgrx::srf_*` helpers, are removed. Call the generated macro with the
PostgreSQL name instead, and extract its result with `.get()` or `.is_true()`.
A generated macro that reads storage or backend state needs an `unsafe` block,
even where the helper it replaces was safe. Several removed helpers checked
their input, while the generated macros check only what the C does.

```rust
// Before
let len = pgrx::varsize_any(ptr);
check_for_interrupts!();

// After
let len = unsafe { pgrx::VARSIZE_ANY!(ptr).get() as usize };
pgrx::check_for_interrupts();
```

`pg_sys::VARHDRSZ` is now `i32` instead of `usize`. `pg_sys::InvalidOid` and
the transaction ID constants such as `pg_sys::FirstNormalTransactionId` keep
their `Oid` and `TransactionId` types. `pg_sys::MemoryContextSwitchTo` and
`pg_sys::heap_getattr` are no longer Rust ports. Like other static inline
functions, they run their generated translation where the build translates the
body, and otherwise call the C function through a guarded binding.
`pgrx::check_for_interrupts()` is the safe replacement for
`check_for_interrupts!`. The expression tree walkers and
mutators, such as `pg_sys::expression_tree_walker`, are functions with one
signature on every supported version. On PG15 the mutators now take a typed
`fn(*mut Node, *mut c_void) -> *mut Node` callback, so remove any `transmute` to
the old `fn() -> *mut Node` type. `IntoDatum` for `f32` and `i8`
now builds the Datum that `Float4GetDatum` and `CharGetDatum` build. The
[C macro guide](docs/src/extension/c-macros.md#migrate-handwritten-helper-calls)
lists every removed helper with its replacement and the check it made, and
describes each of these changes.

## Assert-enabled and release PostgreSQL

`cargo pgrx init` builds PostgreSQL with `--enable-cassert`, and packaged
PostgreSQL is built without it. `pg_sys` now offers the same items against
both, so an extension that compiles against one compiles against the other.

Bindings that only an assert-enabled PostgreSQL declares are gone from every
build. On PostgreSQL 18 these are the functions `MemoryContextCheck`,
`GetLockMethodLocalHash`, `AssertBufferLocksPermitCatalogRead`,
`castNodeImpl` and `stringToNodeWithLocations`, the variables
`Debug_copy_parse_plan_trees`, `Debug_raw_expression_coverage_test`,
`Debug_write_read_parse_plan_trees` and `restore_location_fields`, and the
constants `USE_ASSERT_CHECKING`, `MEMORY_CONTEXT_CHECKING`,
`CLOBBER_FREED_MEMORY`, `DISCARD_CACHES_ENABLED` and
`DEBUG_NODE_TESTS_ENABLED`. To learn at run time whether the server has
assertions, read the `debug_assertions` setting.

Structure members are the exception. A member that only an assert-enabled
PostgreSQL declares, such as `MemoryChunk.requested_size`, is still bound
where it exists, because the structure must have the server's layout. Code
that names such a member compiles only against that build.

PostgreSQL's assertion functions that a release build defines as macros are
macros in both builds: `AssertTransactionIdInAllowableRange!`,
`AssertPendingSyncs_RelationCache!`, `AssertCouldGetRelation!` and
`SlruPagePrecedesUnitTests!`. The last takes a pointer and needs `unsafe`.

```rust
// Before, against an assert-enabled PostgreSQL only
unsafe { pg_sys::AssertTransactionIdInAllowableRange(xid) };

// After, against any PostgreSQL
pg_sys::AssertTransactionIdInAllowableRange!(xid);
```

Generated macros run PostgreSQL's assertions only against a server built with
them. A failed assertion prints PostgreSQL's `TRAP:` line with the Rust file
and line, and aborts the process, as it does in C. A macro needs `unsafe`
exactly where its assert-enabled definition does, so `unsafe` is never unused
in one build and required in the other. `pg_sys::Assert!` is a statement.

## Node macros

`IsA!`, `castNode!`, `makeNode!` and the list macros `lfirst_node!`,
`linitial_node!`, `lsecond_node!`, `lthird_node!`, `lfourth_node!`,
`llast_node!` and `list_nth_node!` are generated.
Their type operand is the Rust type, and all of them need `unsafe`:

```rust
if unsafe { pg_sys::IsA!(node, pg_sys::Query).is_true() } {
    let query = unsafe { pg_sys::castNode!(pg_sys::Query, node).get() };
}
```

`OpExpr`, `DistinctExpr` and `NullIfExpr` are one type in Rust with three node
tags, so none of them is accepted as the type operand. Compare
`pg_sys::nodeTag!` with the tag, or call `PgNode::is_a_ptr`. The
[C macro guide](docs/src/extension/c-macros.md#pass-a-node-type-as-a-rust-type)
describes the type operand.

An argument that a macro's expansion never evaluates must still be a Rust
expression. It is type-checked and not run, so `Assert!(*pointer)` needs
`unsafe` against a release PostgreSQL too.

## Heap tuple helpers

`pgrx::htup::composite_row_type_make_tuple` is now an `unsafe fn`: the caller
must pass a live composite Datum. It also fully detoasts the row, so a stored
composite with a one-byte header is read correctly.

`pgrx::htup::heap_getattr` and `heap_getattr_datum_ex` are now `unsafe fn` as
well. They read the tuple at offsets taken from the descriptor, so the caller
must pass a live tuple whose stored attributes have the same length, alignment,
and pass-by-value flag as the descriptor's attributes in the same positions.
That holds for a tuple formed with the descriptor, and for a stored row of the
same row type after `ALTER TYPE ... ADD ATTRIBUTE` or `DROP ATTRIBUTE`. The
functions' Safety sections also cover offset caching in the descriptor and
missing values that point into it on PostgreSQL 15.0 through 15.4.
`heap_getattr`'s also covers a borrowed `T`, such as `&str`, that points into a
copy that reading detoasts into `CurrentMemoryContext`. A null
`PgBox` or a tuple of another row type was read unchecked before. Both still
panic on an attribute number past the descriptor. `heap_getattr_raw` was
already `unsafe`, and its Safety section now states the same requirements,
including that no reference to the descriptor's attribute entries may be live
across the call. Safe code can no longer hold one, because `PgTupleDesc` now
returns copies, as described below. `PgHeapTuple::get_by_index` and
`get_by_name` remain safe functions, because a `PgHeapTuple` owns a matching
tuple and descriptor. That does not cover a `PgBox<T>`, or a borrowed `T` such
as `&str`, that they read into `CurrentMemoryContext`: do not use one after that
context is reset or deleted, as `get_by_index`'s documentation describes.

`pgrx::htup::DatumWithTypeInfo::into_value` is now an `unsafe fn` too. The
struct's fields are public, so safe code could pair any Datum with any type and
read it as `T`. The caller must now pass a NULL or a value of `typoid` that `T`
can read and whose memory is still live, as the function's Safety section
describes. It still panics on a NULL.

`heap_getattr_datum_ex` now takes `typlen` and `typbyval` from the descriptor's
`attlen` and `attbyval` instead of looking up the attribute's type. A dropped
attribute keeps those but has no type, so it no longer raises "cache lookup
failed for type 0", and its `typoid` is `PgOid::Invalid`.

`PgHeapTuple::get_by_index` reads a dropped attribute as `None`, as SQL does,
instead of raising an ERROR. `set_by_index` and `set_by_name` return
`NoSuchAttributeNumber` for a dropped attribute; before, they raised an ERROR
or, for a value whose `type_oid` is `InvalidOid`, such as a Rust tuple, stored
it. When `T` reads records, as `PgHeapTuple` does, `get_by_index` and
`get_by_name` now return `IncompatibleTypes` for an attribute that is not a row
type, instead of reading its value as a tuple pointer.

## Tuple descriptor attributes

`PgTupleDesc::get`, `PgTupleDesc::iter`, `PgHeapTuple::attributes`,
`PgHeapTuple::get_attribute_by_index` and `PgHeapTuple::get_attribute_by_name`
now return `pg_sys::FormData_pg_attribute` by value instead of a reference. On
PostgreSQL 15 through 17, reading a tuple can make PostgreSQL write an offset
cache into the descriptor's attribute entries, so holding one of the old
references across a read such as `PgHeapTuple::get_by_index` was undefined
behavior. Each value is now a copy, 100 to 112 bytes depending on the
PostgreSQL version, taken when the method runs. It does not see later changes
to the descriptor.

```rust
// Before
let att: &pg_sys::FormData_pg_attribute = tupdesc.get(0).unwrap();
let all: Vec<pg_sys::FormData_pg_attribute> = tupdesc.iter().copied().collect();
let names: Vec<&str> = tupdesc.iter().map(|att| att.name()).collect();

// After
let att: pg_sys::FormData_pg_attribute = tupdesc.get(0).unwrap();
let all: Vec<pg_sys::FormData_pg_attribute> = tupdesc.iter().collect();
let names: Vec<String> = tupdesc.iter().map(|att| att.name().to_owned()).collect();
```

`name()` borrows from the attribute value, so bind the attribute to a variable
before keeping its name, or convert the name to a `String`. Patterns written
against the old reference types, such as `|(_, &att)|` or `*att`, drop the `&`
or `*`. Code like `for (attno, att) in tuple.attributes()` compiles unchanged.

## Tuple descriptor header

`PgTupleDesc` no longer dereferences to `PgBox<pg_sys::TupleDescData>`, so it no
longer gives out a `&pg_sys::TupleDescData`. PostgreSQL changes the reference
count of a relcache or typcache descriptor when code takes or releases a
reference to it, for example when pgrx reads a value of a table's row type into
a `PgHeapTuple` and when that `PgHeapTuple` drops. Holding the old reference
across such a call was undefined behavior. `PgTupleDesc::as_ptr` is now an
inherent method that returns the pointer to pass to PostgreSQL. The header
accessors read the current value of one field each: `len` reads `natts`, `oid`
reads `tdtypeid`, and `typmod` reads `tdtypmod`. The new `refcount` reads
`tdrefcount` and returns `None` for a descriptor that is not reference counted,
and the new `constraints` returns `constr`. Read any other field through
`as_ptr` in `unsafe` code, without creating a reference to the descriptor.

```rust
// Before
let natts = tupdesc.natts as usize;
let refcount = tupdesc.tdrefcount;
let header: &pg_sys::TupleDescData = &tupdesc;

// After
let natts = tupdesc.len();
let refcount: Option<u32> = tupdesc.refcount();
let ptr: pg_sys::TupleDesc = tupdesc.as_ptr();
```

Other `PgBox` methods that the old `Deref` reached, such as `is_null`, are gone.
A `PgTupleDesc` is never null: its constructors now panic on a null pointer.

## `PgVarlena`

`PgVarlena<T>` now holds its value in Rust. Reading one from a Datum copies the
payload into storage aligned for `T`, because PostgreSQL does not align a
varlena's payload, and keeps no pointer into PostgreSQL memory. The value may
therefore outlive the Datum, memory context, or SPI connection it was read
from. `into_pg` and `IntoDatum` allocate a new varlena in `CurrentMemoryContext`
each time, even for an unchanged value, rather than returning the Datum the
value was read from. Payload bytes after the `T` are copied back unchanged.
`PgVarlena::from_datum` panics on a payload shorter than `T` instead of reading
past it.

`into_pg` gives the varlena a one-byte header whenever the payload fits one.
That now includes a value read from a Datum, which used to come back with the
four-byte header that detoasting gave it. C code that reads the result must use
`VARSIZE_ANY` and `VARDATA_ANY`, or detoast it first.

`PgVarlena<T>` now implements `From<T>` for every `T`. Remove any
`impl From<MyType> for PgVarlena<MyType>` of your own, which now conflicts with
it.

`PgVarlena::new` now requires `T: Default` and starts from `T::default()`. It
used to start from zero bytes, which is undefined behavior for a `T` that has no
all-zero value, such as a reference or an enum without a zero discriminant.
Build the value and convert it with `PgVarlena::from(value)`, derive or
implement `Default`, or call the `unsafe` `PgVarlena::new_zeroed` where all-zero
bytes are a valid `T`.

`PgVarlena` stores every byte of its value, padding included. The old `new`
took those bytes from `palloc0`, so a value it created and then filled field by
field stored zero padding. `new` and the new `From` now copy a typed `T`, whose
padding bytes are unspecified, so equal values can store different bytes, and
stale memory can reach disk and WAL. `Default` never guaranteed zero padding,
because it assigned a typed `T::default()` over the zeroed bytes. If a type has
padding and its stored bytes matter, add explicit padding fields so that it has
none, or start from `new_zeroed` and write the fields one at a time.

## `AnyArray` and `AnyElement`

`AnyArray::into::<T>()` read the array as any `T` without checking its type, so
safe code could crash the backend, for example by reading an `int4[]` as
`Array<PgHeapTuple>`. It is now an `unsafe fn` with the same contract as
`AnyElement::into`. Call it as `AnyArray::into::<T>(&values)`, because
`values.into()` on an owned handle resolves to `Into::into`.

The new `value::<T>()` on both types checks the type and returns
`Result<Option<T>, TryFromDatumError>`. It returns `IncompatibleTypes` when `T`
cannot read the value's type, including `InvalidOid`, which a handle has when
its function was called through `fn_call`. It accepts domains, and it reads
composite and `record` values as `PgHeapTuple`.

```rust
// Before
#[pg_extern]
fn int_array_len(values: AnyArray) -> i64 {
    AnyArray::into::<Vec<i32>>(&values).map_or(0, |v| v.len() as i64)
}

// After
#[pg_extern]
fn int_array_len(values: AnyArray) -> i64 {
    match values.value::<Vec<i32>>() {
        Ok(v) => v.map_or(0, |v| v.len() as i64),
        Err(e) => error!("{e}"),
    }
}
```

`FromDatum::try_from_datum` and `try_from_datum_in_memory_context` now return
`IncompatibleTypes` for `InvalidOid` or an OID that names no type, instead of
raising an ERROR. `InvalidOid` no longer matches a Rust type whose own
`type_oid()` is `InvalidOid`, such as `Array<Array<i32>>`.

Values that SPI returns as `AnyElement` or `AnyArray`, for example from
`Spi::get_one::<AnyElement>`, are now copied out of the query's results.
Before, they pointed into memory that was freed when the connection closed. As
for the `&str`, `Array`, and `PgBox<T>` values that SPI already copied, the
copy is made in `TopTransactionContext`, the parent of SPI's memory context, so
it stays allocated until the transaction ends. In a loop that reads many
values, read an owned type such as `String` instead. Elements from iterating
over `&AnyArray` now stay valid after the iterator drops. An `AnyArray` made
from a compressed, out-of-line, or short-header array, such as a table value
passed to a function, now detoasts it once into `CurrentMemoryContext` when the
handle is made, and its elements point into that copy until the context resets.
Iteration used to detoast it again on each pass, in the context current then.
Make the handle in the context where you iterate it: inside `Spi::connect`,
`CurrentMemoryContext` is SPI's, which is freed when the connection closes, so
an `AnyArray` made there, for example by `AnyElement::value::<AnyArray>()`,
must not be iterated after the closure returns.
Elements of an `AnyArray` whose type is a domain over an array now have the
array's element type instead of `InvalidOid`.

Both types are still `Copy` and `'static`. Do not keep a handle, or a borrowed
value read from one, past the call that received it, and read into an owning
type such as `Vec<i32>` or `String` to keep a value.

An array element of a type passed by value in 1, 2, or 4 bytes now has the
Datum that PostgreSQL's `fetch_att` builds when it reads such a value from a
tuple: 2- and 4-byte values are sign-extended, and 1-byte values are widened
as the platform's C `char`. They were zero-extended, so `value::<i64>()` read
an `int4` element of -1 from an `AnyArray` as 4294967295. This applies to
every such type, for example `int2`, `int4`, `"char"`, `oid` and the `reg*`
types, `xid`, `cid`, `date`, and `float4`. It changes the Datum of each
`AnyElement` that iterating an `AnyArray` yields, and of each element of
`Array<pg_sys::Datum>` and `Vec<pg_sys::Datum>`. The raw Datum of an `oid` or
`xid` of 2^31 or more, a negative `date`, or a negative `float4` therefore has
its high bits set, as one read from a tuple already did. Code that reads such
a Datum should keep its low 32 bits, with `as u32` or the generated `DatumGet*`
conversion, instead of rejecting it with `u32::try_from`. Reading the elements
as their Rust type, such as `Vec<pg_sys::Oid>` or `Vec<f32>`, is unchanged.

`FromDatum` for `pg_sys::TransactionId` now keeps the Datum's low 32 bits, as
`DatumGetTransactionId` does. An `xid` of 2^31 or more read from a tuple, for
example through SPI, is no longer `None`, and an `xid` array element, whose
Datum is now the same, reads correctly too.

Reading `Vec<PgBox<T>>` from an `AnyArray` with either method now copies each
element, as described in [`PgBox` array elements](#pgbox-array-elements).

## `PgBox` array elements

Each `PgBox<T>` read from an array is now a copy of the element in a new
allocation in `CurrentMemoryContext`. This covers `Array<PgBox<T>>`,
`Vec<PgBox<T>>`, and `Vec<Option<PgBox<T>>>`, as arguments or read from a
Datum. A box used to point into the array, but an array read from a table is
usually detoasted into a copy, which pgrx frees when the `Array` drops or
before it returns the `Vec`. Those boxes then pointed into freed memory.

A copy holds `size_of::<T>()` bytes and stays allocated until its memory
context is reset or deleted. Each call to `Array::get` and each pass over an
`Array` makes new copies. Writing through a box no longer changes the array. To
read an element type that has its own conversion, such as `pg_sys::Point`, use
`Vec<pg_sys::Point>`, which copies the values without an allocation per
element.

The element type must therefore be passed by reference and have a fixed length
of `size_of::<T>()` bytes, and `T` must need no more than PostgreSQL's
`MAXALIGN` alignment. Reading any other element type as `PgBox<T>` now panics
before reading an element. A copy of a variable-length element, such as a
`path` read as `PgBox<pg_sys::PATH>`, would keep only its header, and
PostgreSQL would read past the copy when it received the box back. A
pass-by-value element, such as an `oid` read as `PgBox<pg_sys::Oid>`, would be
used as a pointer. Read pass-by-value elements as their Rust type, such as
`Vec<pg_sys::Oid>`, and a `jsonb` array as `Vec<JsonB>`. pgrx has no element
type for an array of `path`, `polygon` or a `#[pgvarlena_inoutfuncs]` type.
`pgrx::datum::geo::Path`, `geo::Polygon` and `PgVarlena<T>` copy a whole single
value, for example from `Spi::get_one` or an argument, but they do not
implement `UnboxDatum`, which array elements and `PgHeapTuple::get_by_index`
require. Read such an array as `AnyArray` and each of its elements with
`AnyElement::value`, or unnest it in SQL.

`FromDatum::try_from_datum` and `try_from_datum_in_memory_context` for
`PgBox<T>` apply the same check to a single value and return
`IncompatibleTypes` when it fails. That covers SPI reads such as
`Spi::get_one::<PgBox<T>>`, `AnyElement::value`, and `PgHeapTuple::get_by_index`.
Each such read looks the type's length up in the catalog cache once more.
`FromDatum::from_datum` is unchanged, so a `#[pg_extern]` argument or an
`internal` pointer read as `PgBox<T>` is not checked.

## `PgBox` tuple attributes

`PgHeapTuple::get_by_index` and `get_by_name` now read a `PgBox<T>` as a copy
of the attribute in a new allocation in `CurrentMemoryContext`. The box used to
point into the tuple. A `PgHeapTuple` frees a tuple that pgrx formed or copied,
such as one from `new_composite_type`, when it drops, and `set_by_index` and
`set_by_name` free the tuple they replace. A box read before either could then
point into freed memory.

The copy behaves as it does for [array elements](#pgbox-array-elements): it
holds `size_of::<T>()` bytes, each read makes a new one, writing through it no
longer changes the tuple, and an attribute type that is not passed by reference
with a fixed length of `size_of::<T>()` bytes returns `IncompatibleTypes`. To
read an attribute type that has its own conversion, such as `pg_sys::Point`,
read it as that type.

Other conversions of a single Datum to `PgBox<T>`, such as `#[pg_extern]`
arguments and `FromDatum::from_datum`, still box the Datum's pointer, so the box
can refer to a PostgreSQL struct passed as `internal`. The new
`FromDatum::POINTS_INTO_DATUM` constant marks a type like that, and
`get_by_index` reads such a type with `from_datum_in_memory_context`, which
must return a copy. Set it in a `FromDatum` implementation whose value lets
safe code read the Datum's memory but has no lifetime, as
[`UnboxDatum` implementations](#unboxdatum-implementations) describes.

## `UnboxDatum` implementations

`UnboxDatum` is an `unsafe trait`, and implementations now promise more. When
`As<'src>` does not name `'src`, safe code must not be able to read the Datum's
memory through the value that `unbox` returns, because `Vec<T>` and
`Array::into_iter` keep those values after freeing the array they came from.
`PgHeapTuple::get_by_index` reads such a type through `FromDatum`, so the value
from its `from_polymorphic_datum` must meet the same rule, or the type must set
`FromDatum::POINTS_INTO_DATUM` and return a copy from
`from_datum_in_memory_context`. A handle that wraps a pointer into the Datum
must therefore copy what it points to, or name `'src` in `As<'src>` so that the
compiler ties it to its source. A raw `pg_sys::Datum` meets the rule, because
only `unsafe` code can dereference it.

The new provided method `UnboxDatum::can_unbox(typlen, typbyval)` lets an
implementation reject element types that `unbox` cannot read. `Array` calls it
once for its element type and panics if it returns `false`. It returns `true`
by default; override it if `unbox` reads a fixed number of bytes, as `PgBox<T>`
does.

`#[derive(PostgresType)]` on a type with lifetime parameters now sets
`As<'dat>` to the type with each lifetime replaced by `'dat`, instead of
`Self`; see [Borrowed `PostgresType` values](#borrowed-postgrestype-values).

## Extension type OIDs

`pgrx::wrappers::rust_regtypein::<T>()` no longer looks the type up through
`search_path`, and neither do the `IntoDatum::type_oid` implementations that
call it: those of `#[derive(PostgresType)]` types, `PgBox<T>` and
`PgVarlena<T>`. Before, a type named after a built-in type, such as `Point` or
`Circle`, resolved to the `pg_catalog` type, and a type of the same name earlier
in `search_path` won too. Readers such as `Spi::get_one` then read those values
with the Rust type's layout.

The name is still the last segment of the Rust type's path. For a struct from
`pgrx_pg_sys`, such as `pg_sys::Point` in `PgBox<pg_sys::Point>`, it names the
type in `pg_catalog`. For any other type, it names one of the types that belong
to the extension, in any schema. The extension is the one named by the
`.control` file next to the crate's `Cargo.toml`, which `pg_module_magic!()`
records when PostgreSQL loads the library.

`pg_module_magic!()` reads that name when the crate compiles. Files whose names
start with `.`, such as editor lock files, do not count. If the crate's
directory does not hold exactly one `.control` file, the library records no
name, and looking up any of its own types panics. Cargo compiles the crate
again when a counted file changes or disappears, but not when one is added, so
change a source file after adding one. `cargo pgrx` counts the files the same
way, and it now stops with an error when it finds more than one, where it used
to take whichever it found first.

`rust_regtypein` now raises an ERROR for a type that the extension does not
have, such as one created outside its scripts, when the extension is not
installed in the current database, or when the extension has two types of that
name in different schemas. As before, it also raises one for a shell type.
The row type of a table, view or other relation that is not a composite type,
the array type that PostgreSQL makes for each type, and the multirange type
that it makes for each range type do not count as types of their name.
PostgreSQL 17 and later add those to the extension that owns the table, element
type or range type, and remove them along with it. Earlier versions do not, so
the lookup skips them on every version, including a multirange type that the
extension's own script creates.

A type that another extension or plain SQL creates therefore needs its own
`IntoDatum::type_oid`, which can look the type up with
`pgrx::wrappers::regtypein` and a schema-qualified name, such as
`regtypein("other_schema.other_type")`. A `#[derive(PostgresType)]` type takes
`#[bikeshed_postgres_type_manually_impl_from_into_datum]` for that, and then
implements the datum traits itself. `PgBox<T>` and `PgVarlena<T>` always look
`T` up with `rust_regtypein`. The examples whose `type_oid` returns
`rust_regtypein::<Self>()` rely on their extension's own SQL creating the type.

pgrx does not cache these lookups. Each one lists the types of that name in
every schema and checks in `pg_depend` which of them belong to the extension.
It takes longer when other schemas have types or tables of the same name, up to
the cost of listing the extension's members. pgrx looks the type up for each
value whose type it checks, such as each SPI read and each `fn_call` argument.

## Order of the generated schema

pgrx now builds its schema graph with its own graph code instead of `petgraph`,
so the generated SQL can list the same statements in a different order. pgrx
places each statement after what it declares it needs: the types in a
function's signature that the extension creates, the entries in
`requires = [...]`, and the block that `creates` a type. It does not read the
SQL in an `extension_sql!` block. A schema that worked only because of the old
order can now fail during `CREATE EXTENSION`, often with
`type "..." is only a shell` or an error that an object does not exist.

Check each `extension_sql!` block whose SQL names an object from elsewhere in
the extension, such as a `CREATE CAST` or `CREATE OPERATOR`, and list that
object in its `requires`.

A hand-written `SqlTranslatable` for a type that the extension creates must set
`TYPE_ORIGIN` to `TypeOrigin::ThisExtension`, with `TYPE_IDENT` from
`pgrx::pgrx_resolved_type!(T)`. `TypeOrigin::External` is for a type that exists
outside the extension. pgrx orders nothing after the extension's own SQL for
such a type, so functions and operators that use it can come before the
statement that creates it.

A type built with `extension_sql!` from a shell `CREATE TYPE`, its input and
output functions, and a full `CREATE TYPE` needs `creates = [Type(T)]` on the
block with the full definition. That block must also require the shell block
and the functions. Functions, operators and casts that use `T` then come after
the full definition. PostgreSQL accepts a shell type in a C function's
signature, but `CREATE OPERATOR` and `CREATE CAST` reject one, and with
`creates` on the shell block pgrx can place them between the two statements.

```rust
// Before
extension_sql!("CREATE TYPE my_type;", name = "shell", creates = [Type(MyType)]);
extension_sql!(
    "CREATE TYPE my_type (INPUT = my_type_in, OUTPUT = my_type_out);",
    name = "concrete",
    requires = ["shell", my_type_in, my_type_out],
);

// After
extension_sql!("CREATE TYPE my_type;", name = "shell");
extension_sql!(
    "CREATE TYPE my_type (INPUT = my_type_in, OUTPUT = my_type_out);",
    name = "concrete",
    creates = [Type(MyType)],
    requires = ["shell", my_type_in, my_type_out],
);
```

The [`custom_types` example](pgrx-examples/custom_types/src/hexint.rs) shows
the whole pattern.

## Text array elements

Reading `text` or `varchar` array elements as `&str` or `String`, for example
through `Vec<String>`, `Array<&str>` or `Array<String>`, now checks them as
`FromDatum` for `&str` does. In a `SQL_ASCII` database, an element that is not
valid UTF-8 now panics. In a database with another encoding that is not UTF-8,
such as `LATIN1` or `EUC_JP`, an element with any byte that is not ASCII now
panics, even if its bytes are valid UTF-8. Before, elements were not checked,
so one that was not valid UTF-8 produced an invalid `str`.

## Borrowed `PostgresType` values

A `#[derive(PostgresType)]` type with a lifetime parameter, such as
`struct Part<'a> { word: &'a str }`, borrows from the Datum it is decoded from.
pgrx used to let the caller choose any lifetime for that borrow. `Vec<Part>`
and `Array::into_iter` returned parts whose words pointed into an array that
pgrx had already freed, and a `Part<'static>` argument could be kept after the
call returned.

Each lifetime of such a type is now the lifetime of its source. An argument
borrows for the call. `Array::iter` and `Array::get` return parts that borrow
the `Array`, and `PgHeapTuple::get_by_name` and `get_by_index` return parts
that borrow the tuple. `Vec<Part>` and `Vec<Option<Part>>` no longer compile,
as arguments or read from a Datum, and neither does `Array::into_iter`. Read
the array as an `Array` and use each part while it is alive, or use owned
fields such as `String` to keep values longer.

```rust
// Before
#[pg_extern]
fn words(parts: Vec<Part<'static>>) -> Vec<String> {
    parts.iter().map(|part| part.word.to_owned()).collect()
}

// After
#[pg_extern]
fn words(parts: Array<'_, Part<'_>>) -> Vec<String> {
    parts.iter_deny_null().map(|part| part.word.to_owned()).collect()
}
```

The derive now rejects a field that can only borrow for `'static`, such as
`&'static str`, in a type with its own `inoutfuncs`. The generated JSON input
function already rejected one. Fields of a type with more than one lifetime
parameter may borrow only for its first lifetime, which the JSON input
function also required.

## `pg_binary_protocol` receive functions

The `<type>_recv` function that `#[derive(PostgresType)]` generates for a
`#[pg_binary_protocol]` type is now an `unsafe fn`. It reads its `Internal`
argument as a `pg_sys::StringInfoData`, but safe code can put any value in an
`Internal`, so a safe call could read other memory as one. A Rust caller could
also choose any lifetime, such as `'static`, for a borrowed type it returned,
although the value borrows a copy of the bytes in `CurrentMemoryContext`.
PostgreSQL still calls it as the type's receive function, so SQL,
`COPY ... (FORMAT binary)`, and binary parameters work as before.

Rust code that calls it directly must pass an `Internal` that points to a
`StringInfoData` whose `data` holds `len` bytes and that nothing else accesses
during the call. It must also stop using the value before that memory context
is reset or deleted.

```rust
// Before
let point = point_recv(internal);

// After
// SAFETY: `internal` points to a StringInfoData that only this call uses, and
// `point` is dropped before CurrentMemoryContext is reset.
let point = unsafe { point_recv(internal) };
```

## `Internal` null pointers

PostgreSQL passes some `internal` arguments as a null pointer that is not SQL
`NULL`, such as the second argument of an aggregate deserialization function.
`Internal::initialized` now returns `false` for that value, matching `get` and
`get_mut`, which already returned `None`. `get_or_insert`,
`get_or_insert_default`, and `get_or_insert_with` now allocate a new value
instead of returning a reference through the null pointer. An `Internal` that
is returned unchanged still passes the null pointer back as not `NULL`.

## SPI status codes

`SpiOkCodes` has a `MergeReturning` variant on PG17 and later, so SPI accepts
`MERGE ... RETURNING` instead of panicking on its status code.

## `PgRelation`

`PgRelation::name` and `PgRelation::namespace` now return a `String` instead of
a `&str`. While a relation is open, PostgreSQL rebuilds its relcache entry in
place whenever it processes an invalidation for that relation, including after
this backend runs `ALTER TABLE ... RENAME` on it. `name` borrowed the cached
`pg_class` row, so a name held across such a statement could change, and could
stop being valid UTF-8. `namespace` borrowed a copy that PostgreSQL allocated in
`CurrentMemoryContext`, so it dangled once that context was reset or deleted,
for example when it was returned out of `Spi::connect`. `namespace` now panics
instead of reading a NULL when the namespace does not exist.

`PgRelation` no longer implements `Deref<Target = PgBox<pg_sys::RelationData>>`,
because the rebuild overwrites the whole `RelationData` that a reference from
`Deref` pointed to. `PgRelation::as_ptr` still returns the `pg_sys::Relation` to
pass to PostgreSQL. Use `oid()` instead of `rd_id` and `tuple_desc()` instead of
`rd_att`. Read other fields through the pointer, and copy them out instead of
holding a reference across a call into PostgreSQL.

```rust
// Before
let name: &str = rel.name();
let index = rel.rd_index;
let relam = unsafe { (*rel.rd_rel).relam };

// After
let name: String = rel.name();
let index = unsafe { (*rel.as_ptr()).rd_index };
let relam = unsafe { (*(*rel.as_ptr()).rd_rel).relam };
```

`PgRelation::from_pg` and `from_pg_owned` now panic on a NULL pointer, so code
that checked `is_null()` through `Deref` can drop the check.

## `fn_call` argument types

`pgrx::fn_call::fn_call` and `fn_call_with_collation` now check the type of each
value they pass, from an `Arg::Value` or a `DEFAULT`, against the called
function's parameters before converting any `Arg::Value`. When no function had
parameters of exactly the arguments' types, `fn_call` used to call the only
function of that name, as it does to fill in `DEFAULT` arguments or to call a
polymorphic function, and pass it the arguments unchecked. An `i32` passed to
`textlen(text)` or to `array_ndims(anyarray)` crashed the backend. A mismatch
now returns the new
`FnCallError::IncompatibleArgumentType(argnum, value_type, parameter_type)`,
with the zero-based argument number and both type OIDs.

An argument matches a parameter of its own type, or of a type it is binary
coercible to, such as `varchar` to `text` or a domain to its base type.
`fn_call` applies no other casts, so these calls now return the error:

- An argument whose type needs a cast, such as an `i32` for a `bigint`
  parameter, or an `int4` for a parameter of a domain over `int4`.
- Arguments for polymorphic parameters that PostgreSQL would find inconsistent,
  and arguments for `anycompatible` parameters that PostgreSQL would cast to a
  common type, such as a `numeric[]` and an `int4` for `array_positions`.
- A `DEFAULT` of a polymorphic parameter that is inconsistent with the other
  values. PostgreSQL stores such a default with its own type, such as `int4`
  for `anycompatible DEFAULT 1`, and casts it only when a query calls the
  function. A default written as an untyped literal, such as
  `anyelement DEFAULT 'x'`, has type `unknown` and matches no polymorphic
  parameter.
- An `AnyArray` or `AnyElement` for a parameter other than one of its own type
  or `"any"`, or together with another value for a polymorphic parameter.
- An argument whose type is `InvalidOid`, such as a Rust tuple, or an OID that
  names no type.

`Arg::Null` and a `DEFAULT` that is NULL pass no value, so they are not checked,
and the type of `Arg::Null` or `Arg::Default` still only selects the function.
More arguments than the function has parameters now return
`FnCallError::TooManyArguments` instead of panicking.

`FnCallError` is now `#[non_exhaustive]`, so a `match` on it needs a wildcard
arm. The sealed `FnCallArg` trait has a new `value_type` method, which returns
the argument with an `Arg::Value`'s value replaced by its type OID. The message
of `FnCallError::UnsupportedArgumentModes` now also names `VARIADIC`
parameters, which `fn_call` already rejected with that error.

## `Aggregate::deserial`

`Aggregate::deserial` now takes the serialized bytes and returns `Self::State`.
The function that `#[pg_aggregate]` generated for it also took the current
state, but PostgreSQL requires a deserialization function to take
`(bytea, internal)`, so `CREATE AGGREGATE` failed for any aggregate that
implemented `deserial`. The generated function now has that signature.
PostgreSQL always passes a NULL pointer as its `internal` argument, so the trait
method does not receive it. The generated function is `STRICT`, so PostgreSQL
skips it, and the combine step, for a NULL `bytea`.

```rust
// Before
fn deserial(
    current: Self::State,
    buf: Vec<u8>,
    internal: PgBox<Self::State>,
    fcinfo: pg_sys::FunctionCallInfo,
) -> PgBox<Self::State>;

// After
fn deserial(buf: Vec<u8>, fcinfo: pg_sys::FunctionCallInfo) -> Self::State;
```

## Caught PostgreSQL errors

A PostgreSQL ERROR that pgrx catches stays on PostgreSQL's error data stack
until something calls `FlushErrorState()`, which `PgTryBuilder::execute` does
once a catch handler has handled a `CaughtError::PostgresError`. Rethrowing a
`CaughtError::PostgresError` after that, for example one that a catch handler
returned, used to fail with `errstart was not called` or raise a different error
from the stack. pgrx now copies every field of a PostgreSQL ERROR when it
catches one, and raises that copy when PostgreSQL no longer has the original on
top of its stack. Error handlers such as PL/pgSQL's `GET STACKED DIAGNOSTICS`
see the same error either way. A rethrow while PostgreSQL still holds the error
passes PostgreSQL the original, as before.

`PgTryBuilder::execute` now calls `FlushErrorState()` only once a catch handler
has handled a `CaughtError::PostgresError`, by returning or by raising any other
error. A Rust panic or a `CaughtError::ErrorReport` isn't on the stack, and
flushing after one discarded any ERROR that C code calling into Rust was still
handling.

pgrx 0.18.0 through 0.19.1 flushed the stack whenever they caught an ERROR and
raised every caught error again from a copy of a few of its fields. Since
0.19.2, code that swallows a `CaughtError::PostgresError` without
`PgTryBuilder`, for example with `std::panic::catch_unwind`, leaves the error on
the stack. The stack holds five errors, and PostgreSQL PANICs when it needs a
sixth, so catch such errors with `PgTryBuilder` or call
`pg_sys::FlushErrorState()` after swallowing one.

```rust
// Before
let parsed = std::panic::catch_unwind(|| parse(value)).ok();

// After
let parsed = PgTryBuilder::new(|| Some(parse(value))).catch_others(|_| None).execute();
```

## PG19 buffer lock constants on Windows

On PostgreSQL 19, `pg_sys::BUFFER_LOCK_UNLOCK`, `BUFFER_LOCK_SHARE`, and
`BUFFER_LOCK_EXCLUSIVE` now have bindgen's type, `BufferLockMode::Type`, which
`LockBuffer`, `LockBufferInternal`, and `BufferIsLockedByMeInMode` take. That
type is `u32` on Linux and macOS, as before, and `i32` on MSVC. On Windows with
PG19, code that stores these constants in a `u32` needs a conversion. On
PG15–18 the constants are `u32` and `LockBuffer` takes a C `int`, so code that
builds for several versions should convert with `as _` at the call.

```rust
// SAFETY: `buffer` is pinned by this backend.
unsafe { pg_sys::LockBuffer(buffer, pg_sys::BUFFER_LOCK_SHARE as _) };
```

## `cargo pgrx regress` test names

`cargo pgrx regress` now exits with status 1 when a test name matches no test.
Before, a misspelled name could run only `setup.sql` and pass. A supported
version label such as `pg17` is accepted only as the first argument, so
`cargo pgrx regress pg16 pg17`, which used to run the PG16 tests whose names
contain `pg17`, is now an error. A test whose file name only ends in
`setup.sql`, such as `post_setup.sql`, now runs as an ordinary test; rename it
to `setup.sql` if it was meant to be the setup file.

## Existing `cargo deb` metadata

`cargo pgrx package` now reads `[package.metadata.rpm]` and
`[package.metadata.deb]` on Linux and builds a package for each section it
finds. `cargo deb` reads `[package.metadata.deb]` too, with different keys, so
a section written for it can stop `cargo pgrx package` with an error. For
example, `depends = "$auto"` is rejected. Remove the section, or rewrite it
with the keys described in
[Building RPM and DEB packages](cargo-pgrx/README.md#building-rpm-and-deb-packages).
`cargo pgrx install --sudo` never builds these packages.

## cargo-pgrx's TLS features

cargo-pgrx no longer has `rustls` and `native-tls` features, so remove them
from any `cargo install cargo-pgrx --features ...` command. It always uses
rustls with the platform's certificate store. The default `rustls` feature used
to compile native-tls as well, so installing cargo-pgrx on Linux no longer
needs OpenSSL's development headers. Downloads still honor `ALL_PROXY`,
`HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`.

## `cargo pgrx init` on Linux and macOS

`cargo pgrx init` now unpacks the PostgreSQL source with the `tar` program on
`PATH`, and downloads the `.tar.gz` archive instead of `.tar.bz2`, so GNU tar
needs only `gzip`. Windows downloads are still unpacked by cargo-pgrx itself.

## `pgrx-pg-config`

Code that uses `pgrx-pg-config` directly, rather than through `cargo-pgrx` or
`pgrx-tests`, needs these changes:

- `PgVersion::url` is now an `Option<String>`, and `PgConfig::url` returns an
  `Option<&str>`.
- `cargo::PgrxManifestExt` and `cargo::read_manifest` are gone. Use the
  `cargo_toml` crate to read a manifest, or `cargo::lib_name` for the name of
  its library target.

## Array null bitmaps

`pgrx::nullable::BitSliceNulls` is replaced by `NullBitmap`, which reads
PostgreSQL's array null bitmap without the bitvec crate, and
`RawArray::nulls_bitslice` is gone. To read a raw array's bitmap, pass the bytes
from `RawArray::nulls` and `RawArray::len` to `NullBitmap::new` and query it
through `NullLayout`. `Array`'s `NullableContainer::Layout` is now
`MaybeStrictNulls<NullBitmap<'mcx>>`.

## `pgrx_tests::client`

`pgrx-tests` now talks to its test server with a small built-in client instead
of the `postgres` crate, so extension test builds no longer compile `postgres`,
`tokio`, and their dependencies. `pgrx_tests::client()` and the
`pgrx_tests::postgres` re-export now require the new `client` feature of
`pgrx-tests`:

```toml
[dev-dependencies.pgrx-tests]
version = "=0.20.0"
features = ["client"]
```

`#[pg_test]` functions that use `pgrx_tests::postgres` also need `pgrx-tests`
under `[dependencies]`, because they are compiled into the extension's library.
The `pgrx-tests` README shows the setup.
